# Post-#253 Backlog — Orchestration Plan

## Goal

Clear the eight open issues that accumulated from the #253/#254/#264 shipping
cycle and the 2026-08-13 status review, in three merge-safe batches worked by
parallel agents in isolated git worktrees. The set spans a cross-service
publish hazard (#262), a false-notification trap (#249), two contract
ratifications (#250, #260), a schema contract-drop (#261), an operator-signal
fix (#256), a dashboard field (#266), and a deploy-contract change (#259).

## Approved approach

- **Rubric weighted to correctness** (×3), per the deployment context: active
  production, one live site on port 8000, four active WatchedItems, and two
  sibling services (Archiver, Replicator) consuming Watcher's streams.
- **Hybrid parallelism** — parallel within batches, human review gate between.
- **Worktree ceiling: 4.** Not set by worktree tooling (this repo uses the
  generic `skills/using-git-worktrees/scripts/worktree-create.sh` — plain
  `git worktree`, no ports, vhosts, or DB clones) but by a **shared backing
  service**: one `watcher_test` database behind `TEST_DATABASE_URL`, whose
  session-scoped `test_engine` fixture (`tests/conftest.py:276`) runs
  `create_all` on entry and `drop_all` on teardown. 847 of 1511 tests
  (`-m integration`) depend on it; two concurrent runs corrupt each other.
- **Resolution: four provisioned slots**, created once as superuser because the
  `watcher` role has no `CREATEDB` — the exact friction #259 exists to remove:

  ```bash
  sudo -u postgres psql -c "CREATE DATABASE watcher_a1_test OWNER watcher;"   # a1..a4
  ```

  The names satisfy `src/core/db_safety.py`'s guard, which is a **suffix**
  match (`name.endswith(("_test","_dev"))`, `db_safety.py:83`) — so
  `watcher_a1_test` passes where `test_watcher_a1` would not. Verified with one
  real run: **847 passed in 9.51s** against `watcher_a1_test`. This preserves
  worker self-verification (worker steps 7–9 run before the completion signal).
- **Batch → main: regular merge commit**, matching this repo's precedent
  (`d5a55f5 #267 Merge: …`). Intra-batch worker → batch is fixed at
  fast-forward/regular-merge so `worktree-destroy.sh --base batch/<X>`'s
  ancestor check holds.

## Prioritization rubrics

**Score = (Foundation × 2) + (Correctness × 3) + Scope**, max 18.

| Dimension | 1 | 2 | 3 |
|---|---|---|---|
| **Foundation Leverage** | Standalone improvement | 1–2 other issues benefit | Multiple issues depend on or are simplified by this |
| **Correctness Risk** | Cosmetic / organizational | Edge-case incorrect behavior, runtime failure risk | Data loss, race conditions, silent failures |
| **Scope Clarity** | Requires design discovery | Clear direction, minor decisions needed | Mechanical — implementation is obvious from the issue |

Correctness carries ×3 rather than the standard ×2 because the set's two
highest-consequence items (#262, #249) are both silent-failure classes with a
blast radius outside this service.

Blast radius drives *sequencing*, not score.

### #250 — settled by co-core's contract, which inverts the issue's premise

`FetchPolicyState` (`co_core/pure/models/changes.py:1108`) documents `revoked`
as meaning "**no explicit policy for this host**, *not* 'no limit': the consumer
falls back to its own conservative default", with rule 1 — "a consumer's
fallback default must be **at least as strict as anything the producer would
publish**."

So revocation cannot create a politeness gap. That dissolves the issue's own
design question 2 (the restore race), and it also weakens the counter-argument
currently sitting in `publish_full_policy_set`'s docstring (from `fad9e24`,
#245): publishing a live `min_interval` for a host nobody watches is the only
way that host ends up *looser* than the consumer's fallback.

**Resolved: option (a)** — `build_policy_events` emits `revoked=True` for
`archived_at IS NOT NULL` directly, no tombstone rows — **extended to
`is_active=false`** per design question 3, so the rule is "suspended for any
reason ⇒ no live policy published". Contract rule 2 ("keep republishing revoked
hosts in the full set") is satisfied for free, since archived domains remain in
the `Domain` table. Design question 4 (consumer side) is answered by the same
docstring: the stream is LWW keyed on the `host` **field**, so revoked → live is
an ordinary overwrite.

### #260 — Archiver already answered the question the issue says to ask it

The issue closes with "Worth asking Archiver which of those it is." Read-only
inspection of the sibling checkout answers it:

- `archiver/src/core/services/registry_announcement.py:156` — refuses to
  announce a source as live without non-empty `source_specs`
  ("Announceable-as-live needs non-empty `source_specs` too").
- `archiver/src/core/watcher_provisioning.py:118,211` — always passes
  `list(info_source.source_specs)`.
- Production: **0 of 4** items are spec-less.

Archiver always has specs in hand, so the issue's own logic selects option 3
("makes the schema tell the truth"), and option 2 becomes coherent — in the
issue's words, "unless option 3 lands with it."

**Resolved: 3 + 2 together.** Require `source_specs` at create, and raise
`ExtractionError` if a spec-less item ever reaches `process_watched_item`. The
synthetic `[{}]` at `pipeline.py:146` goes away.

**Residual to state, not discover:** the `info.registry` reconcile path
(`registry_reconcile.py:227`) writes `list(payload.source_specs or [])`, and
co-core's announcement declares `source_specs: list[dict] | None = None`
(`changes.py:1320`). So a spec-less item remains *reachable* over the wire even
after the API door closes — but only for a source Archiver would not announce
as live, which therefore never schedules. Option 2 is what makes that residual
loud instead of silent. Document it; do not add a second gate.

## Conflict zones

### The zone that is not a repo file

`tests/deploy/test_installed_unit_matches_repo.py` asserts **byte-for-byte**
equality between `deploy/watcher.service` and
`/etc/systemd/system/watcher.service`, skipping only when the unit is not
installed — and it is installed on this VM. The installed copy is a
**host-level file outside the repo**, so `git worktree` does not isolate it:
every agent's test run reads the same one.

Two consequences, both load-bearing:

1. **#256 and #262 must be bundled** (Shape A). Both edit the unit. A textual
   merge of two independent edits can succeed and still fail the sync test,
   forcing whichever lands second to redo the install. Bundling makes the
   conflict *impossible* rather than *manageable*.
2. **A1 must NOT run `sudo cp`.** Doing so would flip the live production unit
   mid-batch and turn every co-batch agent's run red on a file none of them
   touched. A1 will see exactly one expected failure —
   `test_installed_unit_matches_repo` — in its own worktree, and must report it
   rather than "fix" it. The orchestrator installs after the batch merges to
   `main`.

Also note `tests/deploy/` cannot collect at all without `TEST_DATABASE_URL`;
`tests/conftest.py:62` raises at import. Every worker loads the env first.

## Key decisions

1. **`deploy/watcher.service` is bundled, not sequenced.** A byte-for-byte sync
   test against a host-level file that no worktree isolates. See *Conflict
   zones*.

2. **A1 does not install the unit.** Expect exactly one failing test on A1's
   branch and on `batch/a`: `test_installed_unit_matches_repo`. This is the
   correct state. The orchestrator runs `sudo cp deploy/watcher.service
   /etc/systemd/system/ && sudo systemctl daemon-reload` after `batch/a` merges
   to `main`, then restarts.

3. **Check the unit's enabled state before restarting.** Run
   `systemctl is-enabled watcher` and `systemctl cat watcher` before any
   repo-documented restart. A unit that is inactive *and* disabled while its
   preset is enabled is a deliberate hold, not a fault — restarting it
   resurrects something an operator stopped on purpose.

4. **#261 is the batch's sole chain-appending agent.** No other issue in the set
   adds an Alembic revision. #259's grants are an operator `psql` step, kept out
   of the chain deliberately so no second agent can compute the same
   `down_revision`. Two migrations generated in one batch fork silently: git
   reports no conflict because the files are different and new, and the break
   appears only on replay.

5. **`docs/ARCHITECTURE.md` §*Redis and the bus* belongs to A1 alone.** A3's
   rule goes in §*Phase 4 contracts*. Both agents want to describe bus
   behaviour; only one owns the section.

6. **AGENTS.md is effectively read-only for this backlog.** It was curated
   8253 → 5964 tokens two commits ago (`6f69ea7`, `d2fa31c`) and is under a
   structural token budget. Route new rules to the detail docs it links.

7. **#259 runs alone and last.** It re-grants roles on the live `watcher`
   database and changes what `TEST_DATABASE_URL` can do — the one change able to
   break the other agents' provisioned slots. Its own body asks for it to land
   "between epics rather than inside one."

8. **Verification-mode asymmetry.** A1 changes when a bus client can be
   constructed. `tests/conftest.py:109` clears `WATCHER_BUS_REDIS_URL` at
   import, so the flag is inert under pytest and no agent's suite exercises the
   new startup assertion. The first real exercise is the post-merge
   `systemctl restart` — if the service fails to start, look at
   `Environment=WATCHER_BUS_ENABLED=1` in the unit before suspecting a defect in
   anyone's diff.

9. **The test-DB slots outlive this backlog.** `watcher_a1..a4_test` stay
   provisioned. Recorded here so the next session inherits the ceiling of 4
   without re-interviewing.
